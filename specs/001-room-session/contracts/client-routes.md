# Client Route Contract: Room Session

**Feature**: `001-room-session`
**Router**: Expo Router 57
**Routes**: exactly `/` and `/room/[code]`

## Shared Preconditions

Before either route performs a protected operation, the application bootstrap:

1. validates the two required public environment variables;
2. selects a lazy browser-`globalThis.localStorage` wrapper from
   `auth-storage.web.ts` on web, with a read-null/no-op path during static export,
   or loads `expo-sqlite/localStorage/install` only from
   `auth-storage.native.ts` on Android/iOS;
3. constructs one typed Supabase client with `persistSession: true`,
   `autoRefreshToken: true`, and `detectSessionInUrl: false`;
4. calls `getSession()` to restore the existing session; and
5. calls anonymous sign-in once only when no persisted session exists.

Concurrent consumers share the same in-flight bootstrap promise, and every room
RPC/subscription waits for it. Reload preserves the participant in browser or
native storage; cleared storage creates a distinct participant. The same client
owns Auth and Realtime so token refresh updates channel authorization. An Auth,
refresh, or environment failure renders a recoverable unexpected-failure state
and never attempts a room mutation as a signed-out caller. Sign-out and
cross-device identity recovery remain outside scope. Static export never invokes
the browser-only Auth bootstrap.

## `/` — Home

### Inputs and controls

- Create-room action.
- One room-code text input.
- Manual-join submit action.
- Retry control for a recoverable create or join failure.

No movie, preference, profile, account, settings, or later-stage controls appear.

### Create flow

1. On one create action, generate one client UUID `creationRequestId` with Expo
   Crypto `randomUUID()`.
2. Disable the initiating control and guard the handler while the call is in
   flight.
3. Call `create_room(creationRequestId)`.
4. On `created` or `already_created`, call `router.replace` with only the
   canonical `/room/<ROOM_CODE>` path. Do not serialize `room_id` or the result
   into route parameters; the room route authoritatively recovers by code.
5. On an exceptional failure, stay on `/`, display a generic recoverable error,
   and let retry reuse the same `creationRequestId`.

No incomplete invitation information is rendered after failed creation.

### Manual join flow

1. Trim surrounding whitespace and uppercase the input.
2. If it does not match `^[0-9A-F]{10}$`, show the malformed-invitation state on
   `/` without navigation or RPC mutation.
3. If valid, navigate to `/room/<CANONICAL_CODE>`.
4. The room route invokes the same `join_room` operation used by direct links.

### Home UI states

- idle;
- anonymous-session loading;
- create in progress;
- manual join/navigation in progress;
- malformed invitation; and
- recoverable unexpected failure with retry.

The in-flight guard improves interaction but does not supply correctness;
PostgreSQL idempotency and locking do.

## `/room/[code]` — Shared Room

### Route input

`code` is one dynamic path segment. The route safely resolves a single string,
trims and uppercases it, and validates `^[0-9A-F]{10}$`. A valid noncanonical
path is replaced with `/room/<CANONICAL_CODE>` without changing the logical join
request. A missing, repeated, or malformed segment renders malformed invitation
and does not call a membership RPC.

Invitation links generated by the app always contain the canonical uppercase
path. On web they are absolute URLs based on `window.location.origin`. On native
they are URLs created for the same path with Expo Linking and the configured app
scheme.

### Join and recovery flow

1. Show joining/loading while Auth bootstrap and route validation complete.
2. Call `join_room` once through the room service for the canonical code,
   including after successful create navigation; the host then receives
   `already_member`.
3. Map `joined` or `already_member` to the room model and start the exact-room
   Realtime lifecycle.
4. Treat an initial accepted result as authoritative. Later Realtime events only
   trigger authoritative exact-column refetches.
5. On reload or reconnect, repeat this same function; the persisted Auth user
   receives `already_member` and does not consume a second seat.

The once-per-code join guard is scoped to the current route generation, so React
effect replay or duplicate navigation cannot dispatch parallel joins. A code
change invalidates the old generation before cleanup and starts one new guarded
join; database idempotency remains authoritative if a duplicate call still
reaches the server.

The link flow and manual flow therefore converge before any backend operation:

```text
absolute invitation URL ─┐
                         ├─> /room/<CANONICAL_CODE> ─> join_room(code)
manual code on / ────────┘
```

### Room UI states

| UI state | Entry condition | Required presentation / action |
|---|---|---|
| Joining/loading | Session bootstrap, RPC, or first accepted-state setup is active | Progress indication; no speculative room state |
| Waiting | Accepted result/refetch says `waiting` | Canonical code, absolute shareable invitation link, `1 of 2`, Waiting |
| Ready | Accepted result/refetch says `ready` | Canonical code, `2 of 2`, Ready; no later behavior starts |
| Malformed invitation | Route/code normalization fails or RPC returns `invalid_code` | Clear malformed message and navigation back to `/` |
| Room not found | RPC returns `not_found` | Clear invalid-room message and navigation back to `/` |
| Room full | RPC returns `full` | Clear room-full message and navigation back to `/`; no room details |
| Recoverable unexpected failure | Auth, network, RPC contract, refetch, or subscription error | Generic non-sensitive message, retry same operation, and navigation back to `/` |

No Supabase user UUID or internal room UUID is displayed. `room_id` is held only
for subscription/refetch. Raw backend errors are not shown.

## Result-to-UI Mapping

A pure mapper accepts the narrowed RPC result and returns one route state. It has
no network, navigation, or subscription side effects. Unknown outcomes, roles,
states, nullability combinations, or participant counts are contract errors and
map to the recoverable unexpected-failure state.

For an accepted result:

- `waiting` requires count `1` and a non-null room ID/code;
- `ready` requires count `2` and a non-null room ID/code;
- `created` and `already_created` require role `host`;
- `joined` requires role `guest`; and
- `already_member` with role `host` permits `waiting`/`1` or `ready`/`2`, while
  role `guest` requires `ready`/`2`.

For `invalid_code`, `not_found`, and `full`, all room, state, role, and count
fields must be null.

## Navigation and Cleanup

- Successful create uses the canonical room route.
- Valid manual input and direct invitation links use that identical route.
- Back/home navigation removes the active Realtime channel.
- Changing the dynamic code first invalidates the old room/subscription
  generation, then removes the old channel before joining/subscribing to the new
  room; late results from the old generation are ignored.
- Retrying does not create another route or backend operation type.
- The route never navigates beyond Ready.
